## 2. Contrat MineLaunched obligatoire

L’URL stable de chaque endpoint sera :

https://<FILES_FQDN>/<slug>/index.php

Elle retourne directement un tableau JSON UTF-8, sans enveloppe de pagination, métadonnées métier ou HTML. La pagination concerne le panel, jamais ce manifeste.

Une entrée de fichier contient exactement :
- path : chemin relatif d’installation, séparateurs « / », sans préfixe de version ;
- checksumSHA1 : SHA-1 réel du contenu, 40 caractères hexadécimaux minuscules ;
- url : URL HTTPS absolue du fichier publié.

Une entrée de dossier contient les mêmes clés, avec path et url terminés par « / », et checksumSHA1 égal au booléen false. Inclure les sous-dossiers et les dossiers vides, avec un ordre déterministe et les parents avant leurs enfants.

Les directives de nettoyage sont des objets distincts placés après les entrées :
{"dirCheckUselessFiles":"mods"}
{"dirCheckUselessFiles":"config"}

Elles sont configurables par endpoint. Pour un nouvel endpoint, proposer « mods » ; « config » exige un choix explicite et un avertissement. Permettre une liste vide. Les dossiers distribués ne sont pas limités à cette liste : kubejs, defaultconfigs, resourcepacks, shaderpacks et toute autre arborescence autorisée doivent fonctionner.

Exemple de fichier de test vide, pas de contenu réel de modpack :
[
  {
    "path": "config/",
    "checksumSHA1": false,
    "url": "https://packs.example.net/atm10a/releases/r001/config/"
  },
  {
    "path": "config/exemple.txt",
    "checksumSHA1": "da39a3ee5e6b4b0d3255bfef95601890afd80709",
    "url": "https://packs.example.net/atm10a/releases/r001/config/exemple.txt"
  },
  {"dirCheckUselessFiles": "mods"}
]

L’extension index.php est uniquement une route de compatibilité : aucun moteur PHP n’est nécessaire. Les informations internes restent dans l’API d’administration.

Conserve les noms autorisés dans path et encode chaque segment d’URL correctement. Teste espaces, accents, apostrophes, Unicode, « + », « # », « % », noms longs et ressemblances avec des séquences d’échappement. Pas de double décodage ni de renommage silencieux. Rejette explicitement les chemins dangereux ou incompatibles avec le profil Windows, notamment les collisions de casse ou de normalisation Unicode.

Pour un endpoint inconnu, non publié ou en erreur sans version précédente, retourne une erreur HTTP explicite, jamais un faux manifeste vide susceptible de provoquer un nettoyage. Si une publication échoue, garde le dernier manifeste valide.

Écris un test de contrat indépendant de l’implémentation. La conformité à ce contrat ne doit pas être présentée comme un test effectué avec le véritable client MineLaunched si celui-ci n’est pas disponible.

## 3. Architecture à réaliser

Utilise des versions stables compatibles, vérifiées dans les documentations officielles au moment du développement, et verrouille les dépendances. Une bibliothèque durable de jobs PostgreSQL est préférable à une file artisanale fragile. Pas de Redis obligatoire sans besoin démontré. Documente tout écart justifié à cette stack.

Déploie avec Docker Compose. Sépare les processus et leurs droits sans multiplier les microservices. La base et le worker n’exposent aucun port public. Aucun conteneur applicatif ne reçoit le socket Docker ou le mode privilégié.

Expose deux listeners distincts :
- IP du serveur:8080 : panel, API privée, uploads et événements ;
- IP du serveur:8081 : manifestes et fichiers publics uniquement.

Adapte les ports s’ils sont occupés et reporte les valeurs réellement utilisées. Le listener de distribution ne doit jamais donner accès à l’administration, même avec un Host falsifié.

Le panel utilise une API de même origine avec des chemins relatifs. Les URL publiques viennent d’une configuration validée, pas d’un Host ou X-Forwarded-Host fourni arbitrairement.

Les fichiers et manifestes publiés doivent rester distribuables par Nginx si l’API, le worker ou PostgreSQL s’arrête. Aucune requête publique de fichier ou manifeste ne doit nécessiter leur disponibilité, recalculer un hash ou reconstruire un inventaire.

## 8. Publication cohérente et rollback

L’URL du manifeste reste stable ; les URL des fichiers incluent un identifiant de version immuable :
https://<FILES_FQDN>/<slug>/releases/<release-id>/<chemin-encodé>

Une publication suit cet ordre : terminer et valider tous les objets ; préparer une version complète ; générer et valider le manifeste ; rendre la version disponible ; basculer atomiquement le manifeste actif.

Le manifeste doit déjà référencer des fichiers réellement présents avant sa visibilité. Prépare les fichiers temporaires sur le système de fichiers approprié et utilise un remplacement atomique ; prévois les étapes de durabilité nécessaires face aux crashs.

Définis explicitement la source de vérité de la publication, un journal/intention de publication et une récupération idempotente. Teste les crashs entre les étapes : le statut de la base doit finir par correspondre à ce que Nginx sert réellement.

Désactive ou adapte les caches de descripteurs, ETag et Last-Modified du manifeste mutable pour empêcher une réponse périmée après la bascule, même lors de publications de même taille dans la même seconde.

Les anciennes versions restent disponibles selon une rétention configurable : proposition initiale de 14 jours minimum et 5 versions récentes, plus les versions épinglées et actives. Ces valeurs sont une politique proposée, pas une garantie pour des téléchargements indéfiniment anciens.

Le garbage collector ne supprime que des données non référencées et hors protection. Il est coordonné avec uploads, publications, sauvegardes et rollbacks, avec mode simulation et compte rendu. Un manque d’espace bloque proprement les nouvelles opérations avant de compromettre la version active.

Un rollback de pack réactive une version conservée sans recalcul inutile. Il ne restaure pas les sauvegardes Minecraft ou les données des joueurs. Distingue-le du rollback du logiciel PackPanel.

## 9. Distribution HTTP et compatibilité reverse proxy

Nginx sert directement manifestes et fichiers. Pas d’autoindex, pas de PHP, pas d’exécution des fichiers déposés, pas de fallback vers la SPA sur le port public.

Fichiers versionnés : téléchargements directs, HEAD, Content-Length correct, Range, réponses 206 et 416 cohérentes, validateurs HTTP appropriés et politique de cache longue pour les réponses réussies immuables. Ne rends pas une erreur 404 durablement cacheable. Ne transforme pas les octets distribués ni les fichiers de configuration.

Sers les contenus déposés avec des en-têtes empêchant leur interprétation active dans le navigateur, sans empêcher leur téléchargement par le launcher. Évite de traiter un fichier HTML/SVG/JS importé comme une page du panel.

La confiance accordée aux en-têtes forwarded est limitée aux proxys connus. Préserve le schéma HTTPS externe sans croire tous les X-Forwarded-* entrants. Pas de CORS permissif avec credentials.
